# SEO & discoverability — design (WSHED-88, 2026-09-06)

How chopinly.com is made findable by search engines and citable by AI
assistants, without adding a build step, a dependency, or a byte of tracking.
The pattern is the alacrity.ai / buildmylease.com playbook
(`claude_ops/docs/sops/llm-seo-optimization.md`), adapted to a hash-routed PWA.

## 1. The shape of the site

```
/                 landing (index.html, hand-written)      canonical home, JSON-LD graph
/app              the app shell (app.html)                noindex; hash routes #/<tool>
/tools            index of the tool pages                 generated
/metronome … /practice-log   one page per tool            generated from content/tools/*.md
/blog, /blog/<slug>          the blog                     generated from content/blog/*.md
/about /privacy /terms /cookies /disclaimer               generated by dev/build-legal.mjs
/sitemap.xml /rss.xml /llms.txt /robots.txt               generated (robots is hand-written)
/.well-known/api-catalog  /.well-known/agent-skills/index.json   generated
/404.html         a real 404 for unknown paths            generated
/welcome          301 → /   (_redirects)
```

**Why the landing moved to `/` and the app to `/app`.** Search engines index
URLs, and the site's home in results should be `chopinly.com`, not
`chopinly.com/welcome`. The old arrangement (app at `/`, JS-redirecting new
visitors to `/welcome`) gave crawlers an empty shell at the root and a
marketing page at a second-class URL. Now `/` is real, crawlable HTML.

**Nobody loses the app.** An inline script at the top of the landing's
`<head>` — before any stylesheet, so before paint — forwards to `/app`
(search + hash preserved) when any of these hold: the page runs in
`display-mode: standalone` (installed PWA), `ws.shell.seen` is set (the app
sets it on every load), the URL carries `?app=1`, or the URL has a `#/…` hash
(a deep link). `?home` overrides the forward so the account sheet's *show
homepage* link works for signed-in users. The manifest's `start_url` is `/app`;
the service worker precaches `/app` and uses it as the offline navigation
fallback, so `/?app=1#/logbook` still opens offline.

Existing installs (start_url `/`) hit the landing, forward before paint, and
pick up the new manifest on their next update. Practice data lives in
localStorage/IndexedDB keyed by origin, not path — nothing moves.

## 2. The generator

`node dev/build-site.mjs` reads `content/tools/*.md` and `content/blog/*.md`
(front-matter Markdown, rendered by the in-repo `dev/lib/markdown.mjs` — a
deliberate subset, node-tested) and writes every generated file listed above,
plus the "From the blog" block inside `index.html` between
`<!-- blog:start -->` and `<!-- blog:end -->`. Output is **committed**;
`tests/site.test.mjs` fails if the committed files differ from `build()`, so a
hand edit to a generated page or a forgotten rebuild is caught by `npm test`.
`node dev/build-site.mjs --check` does the same from the shell.

Tool pages and posts share the document shell (`css/pages.css`, the legal
pages' palette and type): header nav (tools · blog · about · open the app),
breadcrumbs, a brass CTA into the app at the tool's hash route, footer with
every tool, the site links and the documents.

### Per page

| | tool page | post |
|---|---|---|
| `<title>` / description / canonical / OG / Twitter | from front matter | from front matter; `og:type article`, `article:*` meta, `author` |
| OG image | site card `/og/chopinly.png` | its own `/og/blog/<slug>.png` (rendered by `node dev/render-og.mjs --posts` from `dev/og-post.html`) |
| JSON-LD | `SoftwareApplication` (free, browser, offline; `isPartOf` the site app) + `BreadcrumbList` | `BlogPosting` (author Person Leif Taylor, publisher Organization, `about` the tool) + `BreadcrumbList` |
| body | Markdown with h2 sections, ≥300 words | Markdown, ≥900 words, table of contents when ≥3 h2s, tool card, tags, prev/next, related by tag |

The landing carries the site graph: `Organization` (LaLa Solutions LLC),
`Person` (Leif Taylor), `WebSite`, `SoftwareApplication` (Chopinly). Blog index:
`Blog` with its `blogPost` list. Tools index: `CollectionPage` + `ItemList`.

## 3. Crawl + agent surface (SOP §1)

- `robots.txt` — Content-Signals `search=yes, ai-train=yes, ai-input=yes`, explicit allows for GPTBot / OAI-SearchBot / ChatGPT-User / ClaudeBot / Claude-Web / PerplexityBot / Google-Extended / Applebot-Extended, `Disallow: /api/`, sitemap reference.
- `llms.txt` — plain-language guide: what Chopinly is, every tool page with its one-liner, every article, the documents, how to cite. Generated, so it never lists a page that doesn't exist.
- `/.well-known/api-catalog` (RFC 9727 linkset → llms.txt, sitemap, rss) and `/.well-known/agent-skills/index.json` (Agent Skills v0.2.0; `sha256` of llms.txt computed at build so it can't drift).
- `_headers` — one RFC-8288 `Link` header on every page (api-catalog, service-doc, sitemap, alternate rss); content-types for the extension-less files; `X-Robots-Tag: noindex` on `/app`. **`_headers` never applies to Pages Functions**, so `/api/*` gets `x-robots-tag: noindex` from `functions/lib/http.js`.
- `404.html` — Pages serves it with a real 404 for unknown paths (the app is hash-routed, so there is no path-based SPA fallback to lose). Probes like `/wp-login.php` stop soft-404ing as the app shell.
- DNS (WSHED-92): `_index._agents.chopinly.com` SVCB → chopinly.com; DNSSEC on (Cloudflare Registrar publishes the DS itself).
- IndexNow: `/<key>.txt` in the repo root (public by design); `node dev/indexnow.mjs` pings api.indexnow.org with the sitemap's URLs after a deploy.
- **Honest N/A:** no OAuth/OIDC discovery, no `auth.md`, no MCP server card — Chopinly exposes no agent API. Don't add them.

Dashboard-only (Leif, WSHED-91): Cloudflare *Managed robots.txt* off, *Markdown for Agents* on. Account-only (Leif, WSHED-90/93): Google Search Console domain verification, Bing Webmaster Tools.

## 4. Ship loop additions

- Any content change: `node dev/build-site.mjs` (and `node dev/render-og.mjs --posts` for a new post, with the dev server on 8789), then `npm test`.
- Bump `SITE_UPDATED` in `dev/build-site.mjs` when the landing or tool pages change materially (it feeds their sitemap `lastmod`).
- After deploy: the SOP §4 curl block, `tests/e2e/seo.mjs` and `tests/e2e/landing.mjs` against production, then `node dev/indexnow.mjs`.

## 5. What is deliberately not here

No analytics script, no pixels, no A/B tooling — "no tracking" is a promise on
the landing. Search Console is the only measurement, pulled by API (SOP
`google-search-console-api.md`). No keyword-stuffed pages: every tool page
describes the real tool and every article is meant to be read.
